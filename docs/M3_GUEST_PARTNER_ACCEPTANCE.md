### Wallet root-cause follow-up (2026-10-22)

- Route trace: the Guest page gets authentication from the shared session provider; after authenticated state it concurrently requests the same-origin BFF ticket and order lists. Those BFF handlers forward the browser session cookie to the API gateway. Gateway handlers derive the caller actor and invoke `TicketService.listForUser` / `OrderService.listForUser`; repository reads are owner-scoped. The client validates response contracts, then `toTicketWalletData` resolves public event and venue data before transitioning from loading to ready. Errors transition to a distinct unavailable state with retry; a valid empty response maps to the empty-wallet state.
- Defect: `toTicketWalletData` awaited each distinct order/tier/status group’s event/venue resolver serially, so multiple ticket groups accumulated network latency. It now resolves groups in bounded batches of four and preserves stable card order. Session `unknown` had also been treated as logged-out; the wallet now renders a separate session-bootstrap status until the provider resolves.

## QR readiness — M4 handoff

Observed in source/contracts, not fully browser- or device-tested:

- Guest entitlement DTOs expose entitlement/order/event/organization/tier/holder/status/count fields, but no QR credential. The Guest ticket detail intentionally does not display a QR or raw entitlement ID; it states that entry credentials are unavailable. No fake QR was observed.
- Backend `GET /api/v2/tickets/:ticketId/qr` already mints a non-persisted, 30-second rotating payload: `entitlementId:windowStart:HMAC`. The endpoint sets `Cache-Control: no-store`, and authorization allows only the ticket holder or event organization staff; unauthorized IDs are masked as 404. Production configuration requires a 32-character `MAGIC_TICKET_SECRET`.
- Scanner parsing verifies the HMAC and narrow time window. Admission is claimed atomically through the entitlement repository; void/refund-locked entitlements are excluded from the offline manifest and scanner admission checks.
- Defect found and fixed in this continuation: the mint endpoint previously checked holder/staff but not entitlement validity. It could issue a signed QR for a void, redeemed, refund-locked, or fully-scanned entitlement. It now returns a conflict for those states after the ownership check. Focused core service tests (6/6) and QR HTTP route tests (5 passed, 30 unrelated tests skipped) passed; focused ESLint and core typecheck passed.
- Not proven: real Guest wallet QR rendering/refresh, device-camera scan, offline manifest verification under actual device clocks, event-cancelled issuance behavior, refund-to-wallet visual propagation, or cross-device replay handling. Do not treat the existing backend QR endpoint as complete Guest admission UX.

M4 should own the Guest-visible credential lifecycle: ticket/event binding, holder binding, short-lived signed token, refresh/rotation and reissue, expiry, revocation on refund/cancellation/transfer, duplicate scan and atomic single-use policy, offline validation and bounded sync, staff manual lookup, recovery when a Guest loses a device, audit trail, and redaction/no-store policy. Avoid putting raw entitlement IDs into QR content or long-lived stored QR payloads.
