## Slot Requests latency evidence and follow-up

The initial route was tested with Chrome Network set to **No throttling**. The cold route document/RSC took 18.25s. Two identical `/api/bff/slot-requests?direction=incoming` calls took 18.85s and 26.42s; after the screen had loaded, a single manual refresh call took 8.23s. The UI retained the previously loaded data during refresh. This separates the slow connected BFF read from the even slower cold route document request.

Source tracing shows the BFF incoming path first lists the Venue’s venues, then slot requests for each venue, then requests per-item detail in a bounded concurrency pool (up to eight). The initial view therefore waits on a serial list dependency followed by detail fan-out. Browser timing only exposes the aggregate BFF duration, not each upstream Gateway call; the available evidence does not prove which internal request consumed the time. A cold Next.js development route/HMR and duplicate development effect request can contribute to the first-route observation, but do not explain the later single 8.23s BFF call. No latency code change is included because the internal contributor has not been isolated. **Bounded follow-up:** add request-scoped, non-sensitive duration breakdowns for the Venue list, slot-request list, and detail calls; reproduce once on the same connected Venue context; then defer per-request detail loading or otherwise optimize only the proven slow Venue read. Do not expand this into Host acceptance.
